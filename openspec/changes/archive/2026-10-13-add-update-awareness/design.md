# Design

## Context

见 proposal.md。发布包由 `scripts/build-release.ts` 生成 `dist/neko.js`、`dist/gateway.js` 和 `dist/client/`；只有两个 Bun bundle 注入 `NEKO_RELEASE_VERSION`，Vite 页面没有版本。workspace 包的 `0.0.0` 不是产品版本。TUI/Web 通过身份与服务探活复用 gateway，不比较应用版本。浏览器启动仅获取一次 `/api/info`，重连重试原地址；TUI 断线提示重启。

Web 文字草稿和 File 附件均在 composer 的内存 Map 中，普通 reload 会丢失。gateway 的拥有者负责关闭子进程，复用方退出不会关停已有 gateway；本设计保持该语义。

## Goals / Non-Goals

**Goals:** 用同一状态判断回答“安装了吗、运行生效了吗、接下来做什么”；运行版本固定、安装版本可重新读取；提示以一条操作为主，详细版本留在查看入口；允许兼容版本继续工作。

**Non-Goals:** 不增加更新安装或重启的 HTTP/RPC 方法，不管理远程机器上的 Bun，不实现包管理器或事务式安装回滚，不替用户关闭任务，不把已有应用服务的 schema 版本当成软件版本。支持范围仍为 macOS/Linux 的 Bun 全局安装；其他安装方式不自动改写。

## Decisions

### D1. 版本来源与最小兼容握手

在 core 增加浏览器安全的版本类型、稳定 SemVer 比较与状态计算，以及宿主侧安装探测/更新检查模块。CLI、TUI、gateway、Web 静态服务器的 runningVersion 在发布构建时固定；Vite 从同一根 manifest 注入 pageVersion，安装冒烟验证所有产物一致。源码/普通 workspace 运行标为 development，不能用任意工作区 package.json 或用户环境变量冒充发布版本。

宿主从自己的发布产物位置解析所属 `neko-harness/package.json`，校验包名和合法版本，定期重新读取 installedVersion；不缓存为 runningVersion，也不扫描用户项目。文件暂时缺失或替换中，显示 unknown 并下次重读。pageVersion 固定为页面加载的构建，Web 服务的 webVersion 固定为服务进程的构建；服务读取新版磁盘文件不能伪装成新进程。

新增小型服务器级应用信息服务，启动时先在完成 serverId 校验的连接上取得 runningVersion 和独立的 protocolVersion，再绑定目录/会话等业务服务。应用协议初始版本为 1，双方显式声明支持范围；最小信息服务的契约保持稳定，供未来不兼容版本给出有界错误。相同协议下的版本差异只通知；不兼容错误使用可区分类型，TUI/Web spawn 探测不能将它吞成 stale 地址，Web 不为此无限重连。发布前遗留协议兼容不在范围内。

替代方案：只显示 `neko --version` 无法证明 gateway 生效；以 SemVer 主版本决定兼容无法表达 0.x 发布与实际协议边界；把缺少服务一律当网关死掉会错误启动竞争实例。

### D2. 后台检查与本地变化检测分开

宿主请求固定 npm registry 的 `neko-harness` 稳定渠道元数据，检查 HTTP 状态、限制正文为 256 KiB、5 秒超时，验证 `latest` 为正常稳定 SemVer。只使用固定包名，不拼接来自页面或模型的安装地址。没有较新稳定版本时不降级。记录 checkedAt/lastSuccess/latest/checkState，未知与失败不变成 up-to-date。

成功结果缓存 24 小时，后台失败设置 1 小时冷却，损坏/过期缓存忽略；缓存存在用户级 neko 数据目录，与会话数据库分开，用原子替换写入。进程内并发检查共享 Promise，TUI/Web 页面经 gateway 共享检查，浏览器不直接访问 npm。显式 CLI update 和版本页“检查更新”绕过有效期，同进程仍合并请求；失败只在主动查看处提供重试。development 不自动请求 registry。

本地安装文件每 30 秒重新检查一次，连接/窗口恢复前台时可立即检查，不等待 24 小时 registry 缓存；服务状态变化才广播。gateway 关闭释放计时器与 fetch。TUI 当前安装位置与远端 gateway 位置分别计算，不能用 gateway 的安装版本冒充 TUI 自身安装；正常全局安装二者一致。

Web `/api/info` 增加运行中的 webVersion、Web 所属安装版本与当前 gateway 地址/身份，使用 no-store；index.html 同样 no-cache/no-store，避免加载旧入口，hash 资源沿用 Vite。页面每 30 秒以及恢复可见时检查本地信息，隐藏时暂停；重新连接前重新 fetch 信息。服务端发现信息也必须重新解析当前地址，不能永远返回启动时 GatewayHandle 的快照：POSIX 保留配置地址并校验身份，Windows 重新读取对应 serverId 的端口文件，因此随机地址也能重新发现。该 HTTP 读取不拉起或停止 gateway。迟到响应按连接代次丢弃。网络无法访问服务时使用已有连接错误处理，不自动创建后台服务。

替代方案：每个页面轮询 npm 重复且需要浏览器跨域访问；仅启动时检查无法识别命令执行后的安装变化；仅 WS 重连无法识别一直在线的旧页面。

### D3. `neko update` 只升级确认的同一安装

CLI 新增 `update` 路由与帮助。使用当前 Bun 可执行文件取得其全局 bin 路径，并核对全局 `neko` 实际指向当前发布安装的规范化路径及 manifest。支持 Bun 的全局目录配置；无法确认、源码、局部依赖或链接安装拒绝自升级，输出“当前安装方式不支持自升级，请按原方式更新”。不改 PATH，不通过 sudo 提权，不新装第二份工具。

检查时以磁盘安装版本为基准，不能用正在运行的旧 CLI 常量：可能已由另一个终端升级。对该安装获取本地排他锁，记录 pid 并只回收已确认死亡的占用，finally 释放；活跃或无法确认的占用提示稍后重试。显式请求最新稳定版本，已安装不低于目标则不调用包管理器。

有更新时用 argv 调用当前 Bun 的 `add --global neko-harness@<已验证目标版本>`，无 shell 拼接；选择检查时的确切稳定版本避免查询/安装期间 latest 移动。继承用户安装所需环境但不打印环境或 key。安装后重新读取同一全局位置并以新子进程运行 `neko --version`，两者一致且达到目标才成功；新进程用于避免旧模块缓存。权限/网络/验证失败非零退出，输出简短原因及重试操作；详细 Bun 输出只作为该终端命令的诊断，不传到聊天通知。

输出示例：`已是最新版 vX.Y.Z。`、`已升级至 vX.Y.Z。重新启动 neko 生效。`、`升级失败，请重试 neko update。`。成功不表示运行进程已更新。命令不发送停止信号，不调用 gateway，不删数据库/凭据。推荐用户先结束任务并退出相关进程；直接在运行期间升级仍只安装和提示，不能保证被替换文件上的尚未加载模块可继续加载。

替代方案：直接执行裸 `bun add -g ...@latest` 可能更新另一份安装且难验证目标；UI 远程安装扩大权限边界；自动停止拥有者破坏共享任务。

### D4. 提示按下一步去重，不铺开技术状态

状态计算使用 installed、gateway、tui/web、page、latest 的真实值，并单独处理 unknown/development。优先级：协议不兼容 > 本地安装较新且需重启 gateway/静态服务 > 需重启 TUI或仅刷新页面 > 仍有新版可安装 > 一致。当前下一步只显示一条，其余状态在版本页显示；完成当前操作后下一步随新状态出现。普通发布差异不禁用聊天，未知不输出误导动作。

| 场景 | TUI 提示 | Web 提示/操作 |
| --- | --- | --- |
| 可安装更新 | `Update available · Run neko update` | `发现新版本 · 运行 neko update`，复制命令 |
| gateway 或 Web 服务需重启 | `Updated · Restart neko` | `已升级 · 请重新启动本地 neko`，查看步骤 |
| 仅 TUI 需重启 | `Updated · Restart neko tui` | 不适用 |
| 仅浏览器页面需更新 | 不适用 | `页面已更新 · 刷新` |
| 主动检查失败 | `Check failed · Retry` | `检查失败 · 重试` |

主提示最多一句加一个操作；详细页显示版本与一段步骤。“重新启动”说明为：完成任务，退出使用同一数据目录的 TUI/Web 和独立 `neko serve`，再运行 `neko tui` 或 `neko web`。不能建议复用方只退出自己就能更新 gateway；浏览器不提供终止服务按钮。远程页面把执行地点写为“在运行 neko 的电脑上”，复制完整命令。

TUI 增加 `/version` 及补全，复用 PickerPanel 的只读详情/检查动作，不添加 `/update` 安装动作。正常提示采用现有 info 通知并按版本状态键去重，版本查看始终可用；解决后清除对应提醒，状态属于应用而非会话。Web 在顶栏附近提供紧凑非模态提示，设置新增“关于与更新”，升级按钮只复制，检查按钮只查询。复制失败回退为可选中文本，不暗示已安装成功。检查状态独立于连接状态。

替代方案：永久堆叠多条 banner 占据输入区；只靠瞬时 toast 容易漏掉操作；自动弹 modal 会打断正在输入的用户。

### D5. Web 手动刷新保护草稿与附件

只在 gateway 与 Web 静态服务已匹配目标、仅 pageVersion 旧时把“刷新”作为解决动作；其他情况下提供重启步骤。刷新由用户点击，绝不因版本广播自动 reload。

刷新入口在当前会话有文字时，将文字及原 requestId、serverId/workspace/session 标识以有版本的记录写入 sessionStorage；重载后确认数据来源、会话仍存在且属于原工作区再恢复，恢复一次后移除。不自动提交，不把 A 的草稿恢复到 B；没有匹配会话时保留可取回的草稿并说明，不默默丢失。会话归档或数据来源切换不复用旧记录。写入失败保持原页面并提示先复制草稿。会话/工作区选择随该记录恢复；无草稿时仍恢复选择。

File 附件仍是内存资源，不增加 IndexedDB 文件持久化。存在待发送附件、处理/上传或提交未结算时阻止本功能的刷新，提示 `先发送或移除附件，再刷新` 或 `发送中，请稍后刷新`。仅文字输入期间不会失焦；点击刷新前持久保存，成功加载后恢复输入。普通浏览器手动刷新/关闭的全面草稿持久化不是本变更范围。

替代方案：立即 reload 会丢失当前内存草稿；持久化文件引入额外存储与清理复杂度；只警告仍刷新不能满足保留输入。

## Risks / Trade-offs

- [安装工具成功但目标未生效或 PATH 有另一份 neko] → 严格核对同一全局安装；新进程验证，不把进程退出 0 当升级成功。
- [更新覆盖文件而活跃进程仍旧，甚至旧页面 lazy chunk 失效] → 推荐退出后升级；运行版本固定并给出重启步骤，不能把刷新当成所有状态的解法。
- [本地安装轮询读到替换中的 manifest] → unknown 状态暂不提示已最新，下一周期重新读取。
- [启动探测吞掉协议错误] → 类型化兼容错误直接返回，不 spawn 竞争 gateway，不关停拥有者。
- [多个提示与网络失败打扰用户] → 状态优先级、去重和缓存；后台失败静默，详情页保留真实结果。
- [刷新丢失文件或跨会话恢复] → 刷新前阻止未发送附件，草稿绑定工作区/会话与连接数据来源，恢复只读不提交。

## Migration Plan

首次发布一起交付版本元数据、最小兼容握手、CLI 和两端 UI；无需迁移会话数据库。发布前通过本地不同版本构建/fixture 验证混合运行状态，不依赖真实 npm 发布与真实模型请求。安装测试使用隔离 Bun 全局目录和假 registry/安装器，不修改开发者全局工具。

回滚功能代码只撤销提示和 CLI 路由，不改已有消息或凭据。已执行的包安装由用户按原安装方式处理，不宣称自动回滚。发布前遗留客户端兼容不新增；未来改变业务协议时仍保留最小版本握手的可解释拒绝行为。
